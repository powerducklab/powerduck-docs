# التصميم مع المساعد

نمط المواصفة هو المكان الذي تصمّم فيه الواجهة. يربط محادثة الذكاء الاصطناعي بالمستند الحي والمعاينة، كي تصف النية بلغة طبيعية مع الإبقاء على التحكم الكامل في التغييرات الفعلية.

## حلقة الموافقة

لا يعدّل النموذج المستند مباشرة. هذه الحلقة صريحة عمداً.

```text
you describe an intent
        |
the model reads current state and proposes operations
        |
the host validates the proposal
        |
you review a patch card and Apply or Reject
        |
the change is merged into the document
```

هذا الفصل قرار تصميمي محوري. **النموذج** يبرع في فهم النية واقتراح البنى، و**المضيف** حتمي ويتحقّق من كل عملية، و**أنت** توافق على كل تغيير. لا يُعتبَر الاقتراح مطبَّقاً قبل تأكيدك.

## بطاقة التصحيح

تُلخّص البطاقة التغيير وتسرد العمليات الدقيقة، مثل إضافة مسار.

```json
{
  "type": "patch",
  "summary": "Add GET /products endpoint",
  "ops": [
    { "op": "add", "path": ["paths", "/products"], "value": { "get": {} } }
  ],
  "affects": { "paths": ["/paths/~1products"], "resources": ["Product"] }
}
```

مقاطع المسار عناصر مصفوفة، لا سلاسل JSON Pointer. عند إضافة مسار جديد كلياً، يكون الهدف `["paths", "/products"]` وتُنشأ الحاويات الأب تلقائياً.

### تعديلات دقيقة على عملية قائمة

عند تعديل عملية قائمة، لا يُعيد المساعد إرسال العملية كلها — فهذا يمحو كل الحقول غير المكرّرة. بدلاً من ذلك يولّد عمليات صغيرة تدخل العملية ولا تمس إلا ما يتغيّر.

- إضافة معامل استعلام:

```json
{ "op": "add", "path": ["paths", "/products", "get", "parameters", "-"], "value": {} }
```

- توسيع مخطط الاستجابة:

```json
{ "op": "replace", "path": ["paths", "/products", "get", "responses", "200", "content", "application/json", "schema", "properties", "total"], "value": { "type": "integer" } }
```

- تغيير حقل واحد:

```json
{ "op": "replace", "path": ["paths", "/products", "get", "summary"], "value": "..." }
```

تستقبل المصفوفات الإضافات عبر `"-"`، لا إعادة إرسال كاملة. تُحدَّد المعاملات بـ`(in, name)` كي لا تُكرَّر القائمة. يدمج المضيف القيم المقترحة في العملية الحالية ويحافظ على كل ما حُذف.

هذا يجعل الصقل التكراري موثوقاً: قُل «أضف معامل limit هنا» أو «اجعل name إلزامياً»، فيتغيّر ذلك الحقل فقط وتبقى بقية العملية.

## أدوات القراءة تُسند كل اقتراح

قبل الرد، يمكن للنموذج استدعاء أدوات قراءة فقط للحصول على الحالة الدقيقة، لا تخميناً.

- `spec.overview` — العنوان، الإصدار، البروتوكولات، العدّادات، الوسوم، الخوادم، الأمان.
- `spec.listOperations` — كل عملية بصيغة `METHOD /path`، مع الملخصات والوسوم.
- `spec.presentOperations` — يعرض بطاقة قائمة قراءة فقط لكل العمليات.
- `spec.getOperation` — التعريف الكامل لعملية والمخططات المرجعية.
- `spec.getSchema` — مخطط مكوّن واحد، الحقول الإلزامية والأوصاف مشمولة.

عندما لا يكون الشكل الكامل للعملية مرئياً، يجب على النموذج قراءته قبل التعديل.

## الطلبات الواسعة تتقدّم بخطوات

لطلب كبير مثل «ابنِ واجهة تجارة إلكترونية»، لا يُلقي المساعد كل شيء دفعة واحدة.

1. يطرح أولاً **أسئلة توضيحية** حول القرارات الأساسية.
2. بعد الإجابة، يقترح **تصحيحاً مركّزاً في كل مرة**، كل بطاقة بـ2 إلى 5 عمليات.
3. يستمر فقط ما دام أحدث طلب ضمن نطاق ذلك الهدف.

متى ما اتضح النطاق، ينتج المساعد أيضاً `plan` للعمليات المزمع بناؤها، لترى شكل العمل قبل التصحيحات.

## الحماية من الانحراف

يفرض المضيف بعض القواعد لإبقاء العمليات متسقة.

- **المستند الحالي** هو المرجع. إذا لم يُظهر المستند شيئاً، لا يفترض النموذج وجود تصحيح سابق.
- في وضع التركيز لا يتغيّر إلا الهدف النشط (ومخططات المكوّنات المشار إليها صراحةً)؛ بلا تغييرات انتهازية على العمليات الشقيقة.
- ذكر `METHOD /path` آخر يُعامَل كتغيير عملية مقصود.
- تُتتبَّع الاقتراحات المطبَّقة والمرفوضة في السجل كي لا تتكرر التصحيحات القائمة.

عندما لا يكون تفصيل لازم مرئياً، لا يخترعه المساعد: يطرح سؤالاً مركّزاً.

## بطاقات أخرى

ليس كل رد تصحيحاً.

- **بطاقات السؤال** تطلب الاختيار بين خيارات.
- **بطاقات التحقق** تُعلم بضوابط الجودة بحالات نجاح وتحذير وخطأ.
- **بطاقات الإجراء** تقدّم خطوة تالية ملموسة، مثل تشغيل سيناريو أو فتح مساحة.
- **بطاقات جدول البيانات** تعرض بيانات مثال/اختبار ملموسة للعمليات أو المخططات.
